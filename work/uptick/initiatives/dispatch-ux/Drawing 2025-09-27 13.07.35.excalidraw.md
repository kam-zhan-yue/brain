Main Areas of Improvement ^JvXVOTCR

Handling of Fetching in Dispatch Create
- Currently there are so many backend calls in the dispatch create modal, including the debounced nonsense.
- Flake occurs because tests don't know when the emails are done fetching.
- There needs to be clear loading indicators that show when the emails are being loaded and when things are interactive or not.
- Also need to consider if the backend calls are necessary or not. Can we fix this flake entirely in the frontend? What was causing the backend flake to begin with? If the backend is still flakey, we will still have a problem.

Transition between Dispatch Create and Detail
- Currently, there is no distinguishing between a dispatch that is currently in progress and a dispatch that has already been created. When you open a Dispatch Detail, it is vulnerable to the refetching logic no matter if the dispatch has already finished. We can break this up.

We open the DispatchDetailModal
- Using the id in the params, we can use the TaskContext to get the data of the dispatch
- If the status is complete, we show the DetailBody
- If the status is in progress, we show a ProgressBody
- The ProgressBody will keep refetching UNTIL the dispatch is completed
- Then we call the onSuccess and refetch the task, which will update the dispatch and render the DetailBody
- If a dispatch has not completed, we open the DispatchProgressModal, that will do the refetching
- If a dispatch has already been completed (and we know from the task detail), we can open the DispatchDetailModal.
The idea is we don't trigger the refetching logic because we already know the dispatch has been completed. ^Db9eryXv
